# ADR 0003: Decouple schema keys from Google entry IDs via fieldMap

**Status:** Accepted
**Date:** 2026-05-23
**Source:** design spec "Form Submission Proxy" (2026-05-23); working copy in `docs/superpowers/specs/`

## Context

Google Forms identifies each question by an opaque `entry.XXXXXXX` ID, which is what the `formResponse` endpoint expects as urlencoded field names. Exposing those IDs directly in the public API would make request bodies unreadable and would leak an internal Google detail into the API contract. Early versions also stored the entry ID in the schema property's `title`, mixing the human-readable label with the wire format.

## Decision

A `FormDefinition` separates the three concerns:

- `schema.properties` keys are the public API field names. They are human friendly: snake_case keys generated by Gemini when a key is available at generation time, or deterministic `field_N` fallbacks otherwise. The CLI makes this choice once, at generation time.
- The schema property `title` holds the original question text, for documentation and error messages.
- `fieldMap` maps each schema key to its `entry.XXXXXXX` ID. Its keys match `schema.properties` keys exactly.

`submissionUrl` is also stored verbatim in the definition; the Worker never constructs Google URLs itself.

At submission time the Worker validates the body against the schema, then translates keys through `fieldMap` and posts `application/x-www-form-urlencoded` to `submissionUrl` (arrays repeat the entry ID once per value; absent optional fields are omitted).

## Consequences

- API consumers see stable, readable field names and never deal with `entry.` IDs.
- Only `fieldMap` and `submitter.ts` know the Google wire format; the validator and the API surface are Google-agnostic.
- Everything depends on `fieldMap` keys matching `schema.properties` keys: a mismatched key silently drops that field from the submission. The generator produces both from the same field list to keep them in sync (a later fix, commit `c7148a2`, added key deduplication for this reason).
- Whether a form's keys are Gemini-generated or mechanical is frozen at generation time. Regenerating with different options can rename API fields, which is a breaking change for that form's consumers.
